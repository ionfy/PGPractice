# Отчёт о код-ревью расширения pg_array_set

Ревью проводил: Непогодьев М. Д.

Коммит расширения: f98238b4131d8799bd73676f39d37a4b10ddf085

Версия PostgreSQL: 20devel (5fbff0e0890d3ec499b31053be3a6a3276791540)

## Общие выводы

Расширение выполняет заявленный функционал, однако требует исправления критических недостатков. Сборка расширения невозможна без вмешательства в его структуру, аналогична ситуация с тестами.

## Сборка расширения

### Структура расширения
Расширение разбито на 2 разные директории (pg_array_set и task6), Makefile присутствует в каждой. В pg_array_set присутствую только тесты, ввиду чего сборка с помощью make невозможна. В task6 находиться основные файлы расширения, однако отсутствуют тесты.

Вопросы: С чем связана такая структура?

Предложение: Перенос значащих файлов из task6 в pg_array_set для целостности расширения.

### Makefile

Путь до pg_config задан жестко, ввиду чего невозможно собрать расширение без вмешательства в Makefile. Отсутствует команды сборки без использования PGXS (из contrib/).

Предложение: Заменить полный путь 'PG_CONFIG = $(HOME)/pg-install/bin/pg_config' на 'PG_CONFIG = pg_config' для возможности более гибкой сборки. Дополнить Makefile для возможности сборки расширения из дерева исходников (contrib/).

### Итог

Без изменений в структуре расширения:
- PGXS: сборка невозможна.
- contrib/: сборка невозможна.

Внесение частичных изменений (перенос файлов в pg_array_set и исправление PG_CONFIG):
- PGXS: сборка успешна.
- contrib/: сборка не предусмотрена.

**Следующие разделы ревью требуют предложенных изменений для их корректности.**

## Тесты

### Регрессионные тесты

Тесты хорошие. Покрывают большинство сценариев использования функций. При сборке на master-ветке тест 11_type_edge не проходит. Это связано с изменением формата ошибки на текущей версии СУБД. Часть вывода:
```
#  ERROR:  function array_union(integer[], text[]) does not exist
#  LINE 1: SELECT array_union(ARRAY[1,2], ARRAY['1','2']);
#                 ^
# -HINT:  No function matches the given name and argument types. You might need to add explicit type casts.
# +DETAIL:  No function of that name accepts the given argument types.
# +HINT:  You might need to add explicit type casts.
```

Предложение: Добавление альтернативных вариантов ожидаемых результатов тестов для соответствия текущей версии СУБД. Добавление тестов для каждой функции (а не только их части) в блоки 02_text, 06_error_ndim, 07_error_null_elem, 08_null_arg, 09_bool, 10_text_edge, 11_type_edge.

### TAP-тесты

Тесты хорошие. Покрывают большинство сценариев использования функций. Директория с тестами названа tap/, а не t/, что не позволяет их использование без вмешательства в структуру проекта.

Предложение: Замена директории с tap/ на t/. Указание в Makefile полного перечня тестов, вместо TAP_TESTS = 1 для соответствия последним стандартам.

### Общие замечания и предложения

В тестах отсутствую случаи использования больших массивов, указанные в дизайн документе.

Предложение: Добавление тестов на массивы с большим числом элементов.

## Стиль кода

Стиль кода хороший, не мешает его читаемости.

Предложение: Замена имен некоторых переменность для повышения читаемости кода (a -> arr1, b -> arr2, ea -> arr1_elems, eb -> arr2_elems, na -> arr1_size, nb -> arr2_size, tc -> type_cache). 

Нарушено единство кода при возвращении пустого массива:
В array_unique:
```
PG_RETURN_ARRAYTYPE_P(input);
```
В остальных функциях:
```
PG_RETURN_ARRAYTYPE_P(construct_empty_array(ARR_ELEMTYPE(a)));
```

Предложение: Замена возврата пустого массива в array_unique на аналогичный из других функций.

Использование 'pgindent --diff' показало различия в коде со стандартом сообщества PostgreSQL.

Предложение: Использование утилиты pgindent, поставляемой вместе с СУБД, для приведения кода к виду, принятому сообществом PostgreSQL.

## Работа с памятью

### pfree

Отсутствует явный вызов pfree при использовании deconstruct_array. Не критично, так как в СУБД присутствует очистка контекста, однако использование pfree считается хорошим тоном.

Предложение: Добавление pfree для явного освобождения массивов элементов и null-значений, созданных при вызове deconstruct_array.

Аналогична ситуация для массивов result, выделенных с помощью palloc.

Предложение: сохранение промежуточного значения из construct_array(result, ...) в отдельную переменную, после чего освобождение result через pfree.

### TOAST-массивы

Во всех функциях при получении массива с помощью PG_GETARG_ARRAYTYPE_P не учитывается, что они могут быть получены путем создания копии из TOAST-значений, если изначальный их размер был слишком велик. Для понимания этого механизма можно почитать статьи о TOAST-значениях в PostgreSQL. Следует использовать PG_FREE_IF_COPY. Не критично, однако будет считаться хорошим тоном.

Предложение: Добавить во всех функциях PG_FREE_IF_COPY, для всех аргументов типа массив.

## Архитектурные решения

### Соответствие дизайн-документу

В дизайн-документе предложено использование hash-таблиц для сравнений значений в массивах, однако в текущей реализации функций используется линейный проход по массивам. В целом интересное решение, однако требует уточнений перекроет ли дополнительная производительность при поиске накладные расходы на создание hash-таблицы.

### static bool contains(...)

Функция использует оператор равенства полученный из кэша при помощи lookup_type_cache. Хороший подход, позволяет получать операторы сравнения для большинства типов, без явного их создания. Однако, при передачи в функцию массива с типом элементов, оператор равенства для которых не определен, исполнение упадет. Пример:
```
postgres=# SELECT array_intersection(ARRAY['{"a": 10}']::json[], ARRAY['{"a": 10}']::json[]);
server closed the connection unexpectedly
        This probably means the server terminated abnormally
        before or while processing the request.
```

Предложение: Добавить явную проверку на корректность Oid полученного оператора равенства и выход с ошибкой, при его отсутствии. Либо жестко задать допустимые типы в массивах, для защиты от передачи типа без оператора равенства.

### Соответствие типов аргументов

Хотя использование anycompatiblearray и гарантирует, что типы в указанной функции будет приведены к единому, но стоит учитывать, что если функция будет вызвана, например, из другого C-кода, возможна передача массивов разных типов.

Предложение: Использовать проверку соответствия типов, например, Assert(ARR_ELEMTYPE(a) == ARR_ELEMTYPE(b)).
